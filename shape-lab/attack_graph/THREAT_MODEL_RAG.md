## Method

The threat model defines an attacker starting at **any public IP**. Seven user-confirmed TCP reachability facts and observed public pages seed the planner. No login session, IAM grant, database credential, file read, or code execution is seeded. All assets can be selected as a destination; no defense priority is assumed.

For each goal, the retriever builds documents from the sanitized Neo4j projection: assets, topology, network policy, access and ownership rules, principals, route catalog, finding summaries, and endpoint metadata. It ranks documents by goal terms and asset match, preserves finding references and core asset, route catalog, access rule, and principal documents, and caps the prompt at 44 records. It does not send response bodies, attachment contents, screenshot paths, or the SQL dump to the model. This first retriever uses keyword/field scoring plus graph identity. Semantic embeddings are a future option if recall testing shows a need; more model context alone does not fix weak or contradictory evidence.

GLM-5.3 on Ollama Cloud first proposes at most 18 **entry-point vulnerability hypotheses** in JSON. A second focused call receives those candidate capabilities and proposes up to 10 downstream hypotheses whose prerequisites depend on earlier effects or a login made possible by an earlier credential hypothesis. Each identifies an entry point, affected asset, test category, **AND** prerequisites, one principal consequence, cited document IDs, missing evidence, and a verification question. The application checks IDs, capability vocabulary, source references, and bounds. It rejects a SQL injection hypothesis that directly asserts a credential or login session, a purported weakness whose only effect is an already public read, and a compound title that combines alternatives. These are narrow semantic guards, not proof that the other model claims are accurate.

The application adds known ALB API/default routing, observed public access, and ordinary login with a valid credential as separate non-vulnerability actions. The bounded forward planner combines these with hypotheses, checks prerequisites, and strips steps that do not causally support the final outcome. An outcome may require two independent prerequisite branches; both appear in its route. Results include up to 80 conditional routes of at most six steps, plus blocked hypotheses. They are stored as `ThreatModelRun`, `VulnerabilityHypothesis`, `CandidateAction`, and `CandidatePath` in Neo4j. The UI lists hypotheses before routes and renders the chosen chain on the asset graph. There is no autonomous probing or exploit execution.

The public disclosed-ticket read is a known step only when the ticket disclosure condition applies. The snapshot's access-rule enforcement label is inferred, while its supplied observation says unauthenticated reads of disclosed tickets succeeded. The planner grants `public_read:disclosed-ticket-read` after the ALB API route, never private-ticket read from that fact alone.

For example, a route may be ALB `/api/*` forwarding → **possible** SQL injection → **possible** recovery of a reusable manager credential from the database → ordinary login → **possible** authorization failure. Each possible step has its own evidence gap. The known forwarding step happens before any API hypothesis. Database read alone does not prove a plaintext or reusable credential, and a valid manager session does not itself imply unauthorized data access.

`CAN_REACH` is a network fact, never an exploit step. The source-code finding is an offline pattern match in a publicly disclosed ticket attachment; it is **not** evidence of API server source disclosure or code execution. The current access matrix includes analyst inferences; citing an inferred rule does not turn it into an observed enforcement fact. A model-produced privilege gain remains **conditional** even when it cites a real document, until independent weakness or grant evidence is supplied. A route can therefore be structurally reachable while still requiring validation.

## Evaluation needed as the platform grows

1. Maintain a small analyst-labeled set of valid and invalid Bugcamp transitions. Measure retrieval recall, citation correctness, prerequisite completeness, false privilege gains, and path usefulness separately.
2. Confirm actual object checks and store-level grants. Network exposure to RDS, EFS, and S3 does not reveal authentication or IAM policy.
3. Add independently verified weaknesses and permissions as typed evidence. Bind each action to the exact asset, version, principal, and operation. Replan after each new fact.
4. Compare GLM-5.3 candidate routes to an analyst baseline; review conditional branches before treating them as defense priorities. The current snapshot contains no confirmed compromise route.

### First live pilot

Two end-to-end runs were saved with the user-selected Ollama Cloud credential. The RDS-targeted run retained three structurally valid actions and found **zero** complete routes to database read: the proposed database action still required a database credential. The all-assets run retained two actions and one **conditional** path toward the API surface. The local validator rejected two and three other proposed actions respectively for invalid identity, capability, or evidence references. Earlier protocol/output attempts were truncated or malformed and were not saved. These runs verify the integration and show why citation and prerequisite checks are necessary; they do not measure route accuracy or demonstrate a compromise.

## Run the first slice

The UI exposes **Inspect retrieval** and **Generate hypotheses and routes**. The former works without a model key. The latter uses `OLLAMA_API_KEY` from the root `.env`, passed at runtime with `docker compose --env-file ../../.env --env-file .env up -d --force-recreate api` from `shape-lab/attack_graph/`. This keeps the key out of source. The API accepts only `https://ollama.com/v1/chat/completions`. `THREAT_MODEL_EXTERNAL_EXPORT_ALLOWED=true` is an additional server-side gate; without it, generation remains disabled. The selected sanitized evidence is sent to Ollama Cloud when generation is enabled.

The model call uses the existing credential and may incur provider usage. Ollama Cloud does not enforce the JSON format, so a malformed response is rejected locally and not saved. The first run is available at `GET /api/threat-model/latest`; runs remain tied to the scan and survive UI refreshes. The graph API remains loopback only. It has no login or server-side multi-user authorization yet, so this is a local analyst tool.

### Hypothesis-first slice verification

Local tests exercise a five-step API/SQL/database-credential/login/authorization chain, two-branch prerequisites, independent-action exclusion, and rejection of a direct SQL-injection-to-credential leap. The UI has a **Preview local example** button that generates ten explicitly unverified example hypotheses and eighteen causal routes from the supplied architecture, entirely offline and without saving them. The UI production build and API image build passed.

The user explicitly approved exporting selected sanitized ASM and CMDB records to Ollama Cloud. A subsequent two-pass GLM-5.3 run used 44 retrieved records and produced 22 initially accepted hypotheses and 62 structural routes. Local review found over-broad effects: API data access claimed full database access, a cookie theft claim was modeled as session-table access, and ordinary login was labeled a weakness. After tightening the validator and recognizing the reported unauthenticated disclosed-ticket read as a scoped known step, a **local revalidation** of that saved model output produced the current run with **15 hypotheses and 25 conditional routes**, including **20 routes with at least two hypothesis steps**. No new model call was made for that revalidation. The original run-level gap summary was malformed and its text cannot be recovered; each hypothesis retained its specific missing evidence. None of these routes is a confirmed exploit or permission.
